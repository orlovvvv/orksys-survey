# Comprehensive React Component Refactoring Plan

## Context

This plan addresses technical debt in React components exceeding 120 lines of code. The codebase has grown organically, resulting in:

- **Massive files** with multiple components (e.g., `question-renderer.tsx` at 600 lines with 12 components)
- **Boolean prop proliferation** making components hard to reason about
- **Mixed concerns** (UI + state + mutations in single files)
- **Duplicated patterns** across similar components
- **Embedded logic** (debounce, DnD handlers) that should be extracted

The goal is to refactor into focused, single-responsibility components following Vercel's composition patterns and React best practices.

## Backward Compatibility Strategy

All refactored components maintain backward compatibility through barrel exports:

```tsx
// Before: All in one file
// After: Re-export from sub-modules

// survey-builder/index.tsx
export { SurveyBuilder } from "./survey-builder";
export { useSurveyBuilder } from "./context";
export { BuilderCanvas } from "./builder-canvas";
export { BuilderHeader } from "./builder-header";
// etc.
```

Existing imports continue to work:
```tsx
import { SurveyBuilder, useSurveyBuilder } from "@/components/survey-builder";
```

## Design Principles Applied

From Vercel Composition Patterns:
- **Avoid boolean prop proliferation** - Use composition instead
- **Use compound components** - Shared context for complex UI
- **Decouple state from UI** - Provider is only place knowing state implementation
- **Lift state into providers** - Allow sibling access without prop drilling
- **Create explicit variants** - Each variant self-documenting

From React Best Practices:
- **Extract memoized components** - For expensive renders
- **Use functional setState** - For stable callbacks
- **Memoize derived state** - During render, not effects
